# HRM (people management) plan, 2026-11-02

**Goal:** Add an HR module to craftos.app: employee records, leave and approvals, onboarding/offboarding checklists, and recruiting. Sensitive data (salary, ID number, bank account) is stored, encrypted, and visible only to HR.

**Architecture:** Same shape as RMA/WMS: one API module per area (`src/hr-*.ts`) with its own schema string, zod input, `deny()` errors, `audit_events` rows and Chinese/English messages; one frontend module per area (`dist/hr-*.js` + `hr.css`) in the existing workspace shell, both themes and both languages. No new external services.

**Tech:** Node 24, TypeScript, Fastify, PostgreSQL/PGlite, vanilla JS, node:test, linkedom.

---

## Roles

| Who | How set | Can do |
| --- | --- | --- |
| HR admin | `WORKOS_HR_USER_IDS` (deployment config, DingTalk user IDs) only; there is no in-app grant, so an app admin cannot make themself HR | Everything in HR, including revealing sensitive fields |
| Manager | existing `manager_id` reporting line | Non-sensitive profile of direct and indirect reports; approve their leave; interview scorecards when invited |
| Employee | everyone | Own profile; own salary and bank details (masked, reveal own); apply for leave; own checklist items |

Company admins (`WORKOS_EXECUTIVE_USER_IDS`) are **not** automatically HR: salary access is opt-in through the HR list.

## Sensitive data

- Fields: ID number, bank name + account, salary (base, allowances, effective date, history), emergency contact phone.
- Encrypted in the application with AES-256-GCM before they reach the database. Key from `HR_DATA_KEY` (32 random bytes, base64), set only in Render's environment, never in the repo. Each value stores a key id so the key can be rotated.
- Without `HR_DATA_KEY` the sensitive endpoints return 501 and the rest of HR still works (same pattern as DingTalk/Grok).
- Lists always show masked values (`****1234`). Revealing one field is a separate request that requires a reason and writes an audit row (who, whose, which field, when). Reveals are never cached in the browser.
- Values never appear in logs, error messages, AI prompts, notifications or the inbox.
- Compliance note (not legal advice): China's PIPL treats ID numbers and financial accounts as sensitive personal information; it needs a stated purpose and the employee's separate consent. The profile records the consent date and notice version; HR should confirm the wording with counsel.

## Phase 1 — Employee records (foundation)

- `hr_profiles`: hire date, employment type, probation end, contract start/end, job level, work location, status (active / leaving / left), last day.
- `hr_sensitive`: encrypted fields + key id; `hr_salary_history` (encrypted amounts, effective date, reason).
- `hr_documents`: contract scans and certificates (PDF/image, 10 MB, stored like RMA photos), with an expiry date.
- `hr_events`: append-only history (joined, probation passed, contract renewed, title change, left).
- Reminders through the existing inbox: probation ending, contract expiring, document expiring (30/7 days), to HR only.
- Frontend: People → HR tab: directory with status filters, profile drawer, masked sensitive block with Reveal, documents, history, reminders panel.
- Tests: role matrix, manager-chain visibility, masked vs revealed, audit on reveal, no plaintext in DB rows, 501 without key, wrong/rotated key, file limits, both languages.

## Phase 2 — Leave and approvals

- Leave types (annual, sick, personal, marriage, maternity/paternity, bereavement, unpaid), configurable by HR.
- Balances per person per year; HR sets entitlements and adjustments with a reason (statutory annual leave by years worked is shown as a suggestion, not applied automatically).
- Request → manager approves/returns → balance deducted; cancel before start restores it. Half days. Versioned like tasks (409 on stale).
- Team leave calendar; leave shows on the task calendar so overdue tasks during approved leave are flagged, not counted against the person.
- Notifications via inbox, plus DingTalk/email when those are enabled.

## Phase 3 — Onboarding and offboarding checklists

- HR-editable templates (accounts, equipment, training, documents to collect; for leaving: handover, equipment return, account removal).
- Starting one creates tasks through the existing assign system with owners and due dates relative to the start/last day.
- Account deactivation on the last day is a checklist item HR confirms; nothing is deactivated automatically.

## Phase 4 — Recruiting

- Positions (department, hiring manager, headcount, status).
- Candidates: contact, source, resume file, stage (applied → screening → interview → offer → hired / rejected), notes.
- Interviews: schedule, interviewers, structured scorecard per interviewer; interviewers see only their own candidate.
- Offer: proposed salary (encrypted, HR only), status; "hired" pre-fills an HR profile and offers the onboarding checklist.
- Candidate data retention: HR can delete rejected candidates; a reminder after 12 months.

## Release per phase

Full API and frontend suites, typecheck/build; commit frontend; pin its SHA in `deploy/frontend-revision.txt`; push both only after the user approves; check Render deploy and `/health`. `HR_DATA_KEY` and `WORKOS_HR_USER_IDS` must be set in Render by the owner before sensitive features are usable.
