# 客服系统（Customer Service OS）规划

**目标：** 把口碑监控、工单分析、客服政策、产品问题追踪、知识库五件事放进 WorkOS，形成一个闭环：
外部声音 / 工单 → 归类 → 标准答案或产品问题 → 工厂整改 → 知识库更新 → AI 下次直接调用。

**原则：** 复用现有模块（support.ts、public-wiki.ts、quality.js、rma.ts），新增部分也遵循相同模式：
Fastify + PostgreSQL、审计日志、人工确认后才生效，AI 只做建议和归类。不自动对外发帖、不自动发客户邮件。

## 现状盘点

| 需求 | 已有 | 缺口 |
|---|---|---|
| 1 口碑监控 | 无 | 全部新建 |
| 2 工单分析 | `support.ts`：Mac 端从 Zoho Desk 推送工单/草稿/已发回复快照；`knowledge-candidates` 审核流 | 工单主题聚类；判定「出 FAQ / 拍视频 / 产品问题」；频次统计 |
| 3 客服政策 | `support/answers`、`support/sla`（草稿，未激活） | 政策库 + 场景处理手册（SOP），版本化，AI 可调用 |
| 4 产品问题→工厂 | `quality.js` 前端原型（假数据，两级缺陷编码、工厂整改流程） | 后端：问题单、提交工厂日期、工厂回复日期、落实日期、验证关闭 |
| 5 知识库网页 | 原生 Wiki + 公开访问 + AI 助手（`public-wiki.ts`，wiki.1laser.com） | 统一入口与搜索体验；视频/培训/开机课程栏目；挂到 1laser.com/support |

## 模块设计

### M1 口碑监控（Brand Reputation）
- **来源：** Trustpilot、Google 商家评论、Amazon 评价、Reddit（r/lasercutting、r/Laserengraving 等）、YouTube 评论、Facebook 群组、官方论坛、竞品对比帖。
- **采集：** 每日定时任务按关键词（OneLaser、1laser、XRF、型号名）抓取；有官方 API 的走 API（Reddit、Google Business Profile、YouTube），其余用第三方聚合或手动导入 CSV。
- **处理：** AI 判定情感（好评/中评/差评）、主题（质量、物流、售后、软件…）、是否需要回复、紧急度。
- **工作台：** 差评待处理列表 → 指派负责人 → 起草回复（引用标准答案）→ 人工确认后由人发出 → 记录处理结果。
- **看板：** 各平台评分趋势、差评主题 Top10、处理时效。
- 差评若涉及产品缺陷 → 一键转 M4 产品问题。

### M2 工单分析（Ticket Intelligence）
- 在现有 Zoho 快照基础上，每日对新工单做 AI 主题归类，合并成「问题主题」并计数。
- 每个主题给出建议去向（人工确认）：
  - **标准 FAQ** — 文字能讲清 → 生成答案草稿 → 走现有 knowledge-candidates 审核 → 进入 M5
  - **需拍视频** — 涉及操作/装配/调试 → 进入「视频待拍清单」（脚本要点、负责人、截止日、完成后挂链接）
  - **产品问题** — 属于缺陷 → 转 M4
  - **政策问题** — 退换/保修/赔偿 → 对应 M3 政策条目
- 已审核答案标记为 AI 可用；下次同类工单，AI 草稿直接引用标准答案及版本。
- 看板：主题频次、FAQ 覆盖率（多少工单已有标准答案）、视频待拍进度。

### M3 客服政策与场景手册（Policy & Playbook）
- **政策库：** 退货、退款、保修、换机、配件、运费、补偿权限（谁能批多少钱）、跨境/关税等；每条带生效日期、版本、审批人。
- **场景手册：** 常见情况的标准处理流程，如「到货破损」「激光不出光」「物流丢件」「客户威胁差评」「要求退款超期」：判断条件 → 处理步骤 → 话术模板 → 升级条件。
- 政策只有审批通过才对 AI 生效（沿用现有 `policyActivationEnabled` 的思路）。
- 内部可见，可选择部分条目公开到 M5。

### M4 产品问题追踪（Product Issue → Factory）
- 把 `quality.js` 原型落到后端。问题单字段：
  - 缺陷编码（大类 OPT/ELE/MEC/SFW/STR… → 细项）、型号/SKU、批次/序列号范围、影响工单数及关联工单/RMA/差评
  - 严重度、发现日期
  - **提交工厂日期**、工厂对接人
  - **工厂回复方案日期**、根因、纠正措施、预防措施
  - **计划落实日期 / 实际落实日期**（如从哪个批次起改）
  - OneLaser 审核（通过/退回）、**验证日期**、关闭
- 每个状态变更记录时间和操作人，自动计算各阶段耗时；超期标红提醒。
- 工厂账号可选：工厂只看分配给它的问题单，填写方案。
- 与 RMA 打通：维修诊断结果可直接关联问题单。
- 看板：按缺陷编码、型号、工厂的问题分布；平均响应/解决天数。

### M5 知识中心（Support Center，挂到官网 /support）
- 统一一个站点，栏目：**FAQ 标准答案 / 故障排查 / 视频教程 / 开机课程（新手上路）/ 技术培训 / 软件下载 / 政策（公开部分）**。
- 按 **型号 → 问题** 两种入口浏览；全站即时搜索（中英文、型号、错误代码）；AI 助手（已有）基于同一内容回答并给出引用。
- 内部版（员工可见全部，含内部培训）和公开版（只发布标记为公开的内容）同源。
- 上线方式：沿用 wiki.1laser.com，官网 1laser.com/support 跳转或嵌入；或 Shopify 页面反代。需确认官网架构。
- 每篇文章底部「是否有帮助」反馈，回流 M2。

## 分期

1. **P1 产品问题追踪（M4）** — 原型已有，价值直接，范围清晰。
2. **P2 工单分析（M2）** — 依赖现有 Zoho 快照，产出 FAQ/视频清单。
3. **P3 知识中心改版（M5）** — 承接 P2 产出的内容。
4. **P4 政策与手册（M3）** — 需要业务方提供现有政策原文。
5. **P5 口碑监控（M1）** — 依赖外部数据源和可能的付费服务，最后做。

每期：独立分支和 worktree → 测试 → 本地预览 → 确认后再推送上线。

- 工厂人员**自己登录**填写方案，方式是**拉进钉钉**（单独的「工厂」部门），复用现有钉钉登录，不新增登录通道。

## P1 实施要点
- **后端** `src/quality.ts`（新）：
  - 表 `quality_issues`：编号 Q-xxxx、缺陷编码（大类-细项，沿用原型的 OPT/ELE/MEC/SFW/STR/PKG/DOC）、型号/SKU、批次/序列号范围、严重度 S1–S3、状态、工厂（dg 东莞 / jn 济南）、发现日期、影响数量
  - 表 `quality_issue_dates`：每个节点的日期——提交工厂、工厂回复方案、批准方案、计划落实、实际落实（起始批次）、验证、关闭
  - 表 `quality_plans`：工厂方案（根因、纠正措施、预防措施、计划日期），版本化，每版有 OneLaser 审批（通过/退回+理由）
  - 表 `quality_links`：关联工单、RMA 单、差评/论坛帖
  - 表 `quality_events`：完整操作历史；同时写 `audit_events`
  - 状态流：新问题 → 已提交工厂 → 工厂方案待批 → 执行中 → 待验证 → 已关闭（可退回）
- **权限：** 品质负责人（环境变量配置）可建单、提交工厂、批准、验证、关闭；工厂部门成员按 `department_id` 映射到工厂，只能看到并填写分给本工厂的问题单，看不到价格、客户信息等其他模块；其他员工只读。
- **前端** `quality.js`：去掉假数据接后端；问题列表/看板（按缺陷、型号、工厂）；问题详情时间线显示各节点日期和耗时；超期标红；工厂视图只显示本厂问题和方案表单。
- **提醒：** 工厂超过 N 天未回复方案、超过计划落实日未落实 → 站内信（复用 inbox）。
- **测试 + 本地预览**，在独立 worktree 分支 `quality-p1` 开发；推送上线前再确认。
- 上线前需要你做：在钉钉建「工厂」部门并拉入对接人；在 Render 配置品质负责人 ID 和工厂部门映射。
